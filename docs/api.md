# API Reference

Complete reference for all interfaces exposed by pf-payroll: HTTP API and CLI commands.

## HTTP API

This section is the **complete inventory of HTTP endpoints** currently exposed by the application.

### Health and documentation

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Basic healthcheck. Returns `{"status": "ok"}`. |
| `GET` | `/docs` | Swagger UI generated by FastAPI. |
| `GET` | `/redoc` | ReDoc documentation UI. |
| `GET` | `/openapi.json` | Raw OpenAPI schema in JSON format. |

### Market data

pf-payroll does **not** expose its own market-data endpoints. Exchange rates, economic
indices, and income tax brackets are fetched read-only from **pf-rates** over HTTP
through `MarketDataRepository` (configured via `PF_RATES_URL` / `PF_RATES_API_KEY`,
see [Getting Started](getting-started.md)). pf-rates itself owns the default-provider
behavior (SII lookups for `UTM`/`IPC_CL`, `mindicador` fallback for `UF`/`USD`/`EUR`,
optional BCCh credentials) and the startup background sync — see
[pf-rates' API Reference](../../pf-rates/docs/api.md) for `GET /exchange-rates`,
`GET /economic-indices`, `GET /income-tax-brackets`, and `POST /sync`.

### Payroll

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/payroll/import/spreadsheet` | Imports a CSV or XLSX payroll file and persists employers, periods, and items. Runs on the same transactional-scope machinery as `/payroll/import/json`: the whole import + reconciliation pipeline runs inside one SAVEPOINT. `mode` is sent as a multipart form field alongside `file` (not JSON, since this is a file upload) and defaults to `"commit"` -- unchanged behavior for existing callers -- which only actually commits once every period reconciles cleanly (see `validated`/`saved` below); a genuine declared-vs-computed conflict rolls everything back and fails the request with 400 instead of persisting partially-reconciled data. `mode="validate"` runs the identical pipeline against the same SAVEPOINT machinery but always rolls back regardless of the result, returning 200 with `validated: false` and each period's own warning instead of failing -- letting a caller preview an entire file's conflicts in one request before ever touching the database. On the commit-mode 400, `detail` is not a bare string: it is `{"message": str, "conflicting_periods": [...]}`, where `conflicting_periods` lists *only* the period(s) that actually conflicted (same shape as a normal response period, `id` always `null` since nothing was persisted) -- a multi-period file with one bad period does not force scanning every clean one to find it. If related market data is missing, it first fetches the exact dates/periods needed for the imported payroll so calculations can continue immediately; when the imported payroll already includes the pension and health contribution rows, the import flow also computes `UNEMPLOYMENT_INSURANCE` and `INCOME_TAX` automatically. Any unresolved market-data remainder can still be retried in the background sync flow. |
| `POST` | `/payroll/pdf-preview` | Read-only: extracts a preview of the payroll rows found in one or more uploaded PDF payslips, using versioned templates (see `infrastructure/pdf_import/templates/`). Accepts a batch: send multiple `files` parts in one multipart request (e.g. several distinct liquidaciones for different employees or periods) and get back a JSON array with one preview object per file, in upload order -- each PDF is extracted fully independently, so one payslip's template match or resolved rows never affect another's. A single file still works, just wrapped in a one-element array. Deliberately not under `/payroll/import/*`: unlike the other two routes below, this one never imports anything -- it is a pure PDF-to-JSON extractor and never touches the database for writes. Never fails outright over template mismatches -- a PDF matching no known template still contributes an array entry with every row marked unresolved (`concept_code: null`) instead of failing the batch; however, if any file in the batch has no filename at all, the whole request fails with 400/422 and nothing is returned, rather than silently dropping just that one entry. `payment_date` is resolved from the matched employer's real configured payment-date rule (a read-only lookup -- "never persists" only ever meant no writes) when that employer is already registered; falls back to a generic "last business day of the month" guess otherwise, which a human can still correct by hand before `POST /payroll/import/json`. |
| `POST` | `/payroll/import/json` | Confirms one or more already-structured payslip periods (the request body is `{"mode": ..., "periods": [...]}`, where each `periods[]` block is typically one element of the array returned by `/payroll/pdf-preview`, edited by a human) through the same pipeline as `POST /payroll/import/spreadsheet`. `periods` must have at least one element (400 if empty), and no two elements may share the same `(employer, period_year, period_month)` (400 if they do) -- each block owns its own header (`payment_date`, `employment_contract_kind`, `declared_net_pay_clp`) independently, so silently merging two "same period" blocks would mean picking one's header over the other's with no signal to the caller; concatenate their `rows` client-side first if that's genuinely one period. `mode` applies once to the whole batch, not per period. `mode="commit"` (default) persists everything, but fails outright (400, nothing persisted) if any row in any period still has an unresolved `concept_code`, *or* if the reconciliation pipeline finds a genuine declared-vs-computed conflict on net-pay, contributions, or complementary insurance for any period -- see `validated` below for exactly what counts as a conflict. On the reconciliation-conflict 400 specifically (not the unresolved-`concept_code` one, which stays a plain string), `detail` has the same structured `{"message": str, "conflicting_periods": [...]}` shape described under `POST /payroll/import/spreadsheet` above. `mode="validate"` runs the identical computation pipeline against a SAVEPOINT that is always rolled back at the end regardless of what it finds -- rows with an unresolved `concept_code` are excluded from that pipeline and reported back via the response's `unresolved_rows` field instead of failing the request, each entry identified by `period_index` (position in `periods`) plus `row_index` (position within that period's own `rows`) (`POST /payroll/import/spreadsheet` has no equivalent, since a CSV/XLSX row always carries a resolved `concept_code`; `unresolved_rows` is always `[]` there). Note: pf-rates may still cache market data it resolves during either mode; that cache is not rolled back. In `mode="validate"`, each returned period's `id` is always `null`: the INSERT genuinely happens (so contributions/tax/warnings are real) but is rolled back, and that id will never exist in the database -- Postgres sequences are not transactional, so the underlying `BIGSERIAL` value is permanently consumed either way (a harmless gap), but the row itself is not persisted. Never treat a `validate` response's `id` as a real reference. The response also echoes back `mode`, since `period_count`/`item_count` describe rows genuinely persisted only when `mode="commit"` -- in `mode="validate"` those same counts describe what *would* be persisted if resent as a commit. Two more response fields describe the outcome: `validated` is `true` when every row resolved a `concept_code` and no period has a *genuine* net-pay/contribution/complementary-insurance conflict -- "pending" reconciliation states (e.g. a projected period whose plans are not assigned yet, or a temporary market-data gap) do not count as conflicts and never block a commit, since there is nothing wrong there, just nothing to compare yet; `saved` is `true` once `mode="commit"` actually persisted the write, or `null` in `mode="validate"` (nothing was persisted, so "was it saved" does not apply). Because a genuine conflict now fails the request instead of returning it, a 200 response in `mode="commit"` (`POST /payroll/import/spreadsheet` included -- both endpoints share this exact `mode`/`validated`/`saved` contract) always has `validated: true` and `saved: true` together. Each entry in `periods[]` also carries its own `validated` boolean, mirroring the exact same "no *known* conflict" semantics as the top-level `validated` but scoped to that one period, so a caller can tell which specific period(s) need attention without recomputing anything client-side; `validated_period_count` and `unvalidated_period_count` (which always sum to `len(periods)`) are a quick summary over that per-period flag, so a large batch does not have to be scanned entry-by-entry just to know how many periods came back clean. Both response fields are shared with `POST /payroll/import/spreadsheet` too. |
| `GET` | `/payroll/period-range` | Returns the current payroll period plus 12 previous and 12 next period date ranges. Each item exposes `net_pay_clp` and a single `position` field with `previous`, `current`, or `future`. The current period is the latest payroll with `declared_net_pay_clp` present and `payment_date <= today`. When none exists, the endpoint falls back to the current calendar month and infers missing periods from the configured employer payment rule or the default last Chilean business day of month. |
| `GET` | `/payroll/summary` | Lists payroll period totals from `PAY_MV_SUMARY`. |
| `GET` | `/payroll/{period_id}` | Returns a payroll period with employer, items, selected plans, and summary. |
| `POST` | `/payroll/{period_id}/assign-plans` | Assigns pension and health plan snapshot ids to a payroll period. |
| `POST` | `/payroll/{period_id}/compute-contributions` | Computes pension, health, and unemployment insurance discounts. |
| `POST` | `/payroll/{period_id}/compute-tax` | Computes Chilean monthly income tax withholding. |
| `POST` | `/payroll/{period_id}/review` | Marks a payroll period as `reviewed` once required computed items exist. |
| `POST` | `/payroll/{period_id}/deflate` | Converts nominal payroll totals into real CLP using an economic index such as `IPC_CL`. |

## CLI

Run the CLI with:

```bash
python -m payroll.interfaces.cli.main <command>
```

Or use the Makefile shortcut for payroll import:

```bash
make import-payroll CSV_FILE=docs/payroll-input.csv
```

Available commands:

| Command | Purpose |
| --- | --- |
| `health` | Basic healthcheck. |
| `import-payroll <file>` | Imports a CSV/XLSX payroll file. Runs on the same transactional-scope machinery as `POST /payroll/import/spreadsheet`: the whole import + reconciliation pipeline runs inside one SAVEPOINT, and only actually commits once every period reconciles cleanly -- a genuine declared-vs-computed conflict rolls everything back and fails the command with a non-zero exit code instead of persisting partially-reconciled data. On that failure, stderr prints the plain message first, then (on its own line) the same structured `{"message": str, "conflicting_periods": [...]}` detail as the HTTP endpoint's 400 `detail` -- listing only the period(s) that actually conflicted, so a multi-period file does not require scanning every clean one by hand. |
| `template-test <pdf>` | Previews a payroll PDF against the current templates without persisting anything (no DB access at all, unlike `POST /payroll/pdf-preview`) -- prints which template matched (if any) and which rows are still unresolved. `payment_date` is always the generic "last business day of the month" guess here, never the employer's real configured rule, since this command has no database to read it from. Helper for building/adjusting `infrastructure/pdf_import/templates/*.json` by hand. |
| `summary` | Lists payroll period summaries. |
| `period-detail <period_id>` | Returns one payroll period with detail. |
| `plan-snapshots` | Lists available pension and health plans. |
| `assign-plans <period_id> <pension_plan_id> <health_plan_id>` | Assigns period plan snapshots. |
| `compute-contributions <period_id> <pension_plan_id> <health_plan_id> [--uf-value-clp]` | Computes social-security discounts. |
| `compute-tax <period_id> [--utm-value-clp]` | Computes income tax withholding. |
| `review <period_id>` | Marks a period as reviewed. |

All CLI commands emit JSON except `health`.
