# API Reference

Complete reference for all interfaces exposed by pf-payroll: HTTP API and CLI commands.

## HTTP API

This section is the **complete inventory of HTTP endpoints** currently exposed by the application.

### Health and documentation

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Basic healthcheck. Returns `{"status": "ok"}`. |
| `GET` | `/docs` | Swagger UI generated by FastAPI. |
| `GET` | `/redoc` | ReDoc documentation UI. |
| `GET` | `/openapi.json` | Raw OpenAPI schema in JSON format. |

### Market data

pf-payroll does **not** expose its own market-data endpoints. Exchange rates, economic
indices, and income tax brackets are fetched read-only from **pf-rates** over HTTP
through `MarketDataRepository` (configured via `PF_RATES_URL` / `PF_RATES_API_KEY`,
see [Getting Started](getting-started.md)). pf-rates itself owns the default-provider
behavior (SII lookups for `UTM`/`IPC_CL`, `mindicador` fallback for `UF`/`USD`/`EUR`,
optional BCCh credentials) and the startup background sync — see
[pf-rates' API Reference](../../pf-rates/docs/api.md) for `GET /exchange-rates`,
`GET /economic-indices`, `GET /income-tax-brackets`, and `POST /sync`.

### Payroll

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/payroll/import/spreadsheet` | Imports a CSV or XLSX payroll file and persists employers, periods, and items. Runs on the same transactional-scope machinery as `/payroll/import/json`: the whole import + reconciliation pipeline runs inside one SAVEPOINT. `mode` is sent as a multipart form field alongside `file` (not JSON, since this is a file upload) and defaults to `"commit"` -- unchanged behavior for existing callers -- which only actually commits once every period reconciles cleanly (see `validated`/`saved` below); a genuine declared-vs-computed conflict rolls everything back and fails the request with **422** instead of persisting partially-reconciled data. `mode="validate"` runs the identical pipeline against the same SAVEPOINT machinery and always rolls back regardless of the result; if the result is not fully validated, the request fails with the same **422** instead of returning 200 with `validated: false` -- a caller still previews an entire file's conflicts in one request before ever touching the database, just via the error's `detail` now instead of a 200 body. Both modes share the exact same structured `detail`: it is `{"message": str, "conflicting_periods": [...]}`, where `conflicting_periods` lists *only* the period(s) that actually conflicted (same shape as a normal response period, `id` always `null` since nothing was persisted) -- a multi-period file with one bad period does not force scanning every clean one to find it. If related market data is missing, it first fetches the exact dates/periods needed for the imported payroll so calculations can continue immediately; when the imported payroll already includes the pension and health contribution rows, the import flow also computes `UNEMPLOYMENT_INSURANCE` and `INCOME_TAX` automatically. Any unresolved market-data remainder can still be retried in the background sync flow. |
| `POST` | `/payroll/pdf-preview` | Read-only: extracts a preview of the payroll rows found in one or more uploaded PDF payslips, using the active templates read from pf-db's `PAY_PDF_TEMPLATE`/`PAY_PDF_TEMPLATE_FIELD` tables (managed via the `/payroll/templates*` endpoints below -- no longer a git-tracked JSON file). Accepts a batch: send multiple `files` parts in one multipart request (e.g. several distinct liquidaciones for different employees or periods) and get back a JSON array with one preview object per file, in upload order -- each PDF is extracted fully independently, so one payslip's template match or resolved rows never affect another's. A single file still works, just wrapped in a one-element array. Deliberately not under `/payroll/import/*`: unlike the other two routes below, this one never imports anything -- it is a pure PDF-to-JSON extractor and never writes to the database (it does now read from it, to fetch the active templates and, when the matched employer is already registered, its real payment-date rule). Never fails outright over template mismatches -- a PDF matching no known template still contributes an array entry with every row marked unresolved (`concept_code: null`) instead of failing the batch; however, if any file in the batch has no filename at all, the whole request fails with 400/422 and nothing is returned, rather than silently dropping just that one entry. `payment_date` is resolved from the matched employer's real configured payment-date rule (a read-only lookup -- "never persists" only ever meant no writes) when that employer is already registered; falls back to a generic "last business day of the month" guess otherwise, which a human can still correct by hand before `POST /payroll/import/json`. |
| `POST` | `/payroll/import/json` | Confirms one or more already-structured payslip periods (the request body is `{"mode": ..., "periods": [...]}`, where each `periods[]` block is typically one element of the array returned by `/payroll/pdf-preview`, edited by a human) through the same pipeline as `POST /payroll/import/spreadsheet`. `periods` must have at least one element (400 if empty), and no two elements may share the same `(employer, period_year, period_month)` (400 if they do) -- each block owns its own header (`payment_date`, `employment_contract_kind`, `declared_net_pay_clp`) independently, so silently merging two "same period" blocks would mean picking one's header over the other's with no signal to the caller; concatenate their `rows` client-side first if that's genuinely one period. `mode` applies once to the whole batch, not per period. `mode="commit"` (default) persists everything, but fails outright (**422**, nothing persisted) if any row in any period still has an unresolved `concept_code`, *or* if the reconciliation pipeline finds a genuine declared-vs-computed conflict on net-pay, contributions, or complementary insurance for any period -- see `validated` below for exactly what counts as a conflict. Both of those 422s share the same structured `{"message": str, "conflicting_periods": [...], "unresolved_rows": [...]}` shape described under `POST /payroll/import/spreadsheet` above (plus the `unresolved_rows` field, empty/omitted when not relevant to that particular failure). `mode="validate"` runs the identical computation pipeline against a SAVEPOINT that is always rolled back at the end regardless of what it finds; rows with an unresolved `concept_code` are excluded from that pipeline so the rest of the batch still gets genuine computations, but if any were excluded -- or the pipeline finds a genuine reconciliation conflict -- the request fails with the same **422** instead of returning 200, reporting them back via the error's `detail.unresolved_rows` field, each entry identified by `period_index` (position in `periods`) plus `row_index` (position within that period's own `rows`) (`POST /payroll/import/spreadsheet` has no equivalent, since a CSV/XLSX row always carries a resolved `concept_code`). Note: pf-rates may still cache market data it resolves during either mode; that cache is not rolled back. In `mode="validate"`, each returned period's `id` is always `null`: the INSERT genuinely happens (so contributions/tax/warnings are real) but is rolled back, and that id will never exist in the database -- Postgres sequences are not transactional, so the underlying `BIGSERIAL` value is permanently consumed either way (a harmless gap), but the row itself is not persisted. Never treat a `validate` response's `id` as a real reference. The response also echoes back `mode`, since `period_count`/`item_count` describe rows genuinely persisted only when `mode="commit"` -- in `mode="validate"` those same counts describe what *would* be persisted if resent as a commit. Two more response fields describe the outcome: `validated` is `true` when every row resolved a `concept_code` and no period has a *genuine* net-pay/contribution/complementary-insurance conflict -- "pending" reconciliation states (e.g. a projected period whose plans are not assigned yet, or a temporary market-data gap) do not count as conflicts and never block a commit, since there is nothing wrong there, just nothing to compare yet; `saved` is `true` once `mode="commit"` actually persisted the write, or `null` in `mode="validate"` (nothing was persisted, so "was it saved" does not apply); `saved` is **never `false`** -- that would mean "we attempted `mode="commit"` and it did not persist", which is exactly the condition the 422 above already rejects before any response is built, so there is no 5xx (or any other status) reporting a "failed save" separately from the 422 covering `validated`. Because a genuine conflict now fails the request instead of returning it -- in *either* mode, `mode="validate"` included, unlike before -- a 200 response always has `validated: true`, whether `mode="commit"` (where `saved: true` too -- `POST /payroll/import/spreadsheet` included, both endpoints share this exact `mode`/`validated`/`saved` contract) or `mode="validate"` (`saved: null`). Each entry in `periods[]` also carries its own `validated` boolean, mirroring the exact same "no *known* conflict" semantics as the top-level `validated` but scoped to that one period, so a caller can tell which specific period(s) need attention without recomputing anything client-side; `validated_period_count` and `unvalidated_period_count` (which always sum to `len(periods)`) are a quick summary over that per-period flag, so a large batch does not have to be scanned entry-by-entry just to know how many periods came back clean. Both response fields are shared with `POST /payroll/import/spreadsheet` too. |
| `GET` | `/payroll/period-range` | Returns the current payroll period plus 12 previous and 12 next period date ranges. Each item exposes `net_pay_clp`, an `increase` boolean, and a single `position` field with `previous`, `current`, or `future`. Unlike every other money field in this API (always a JSON string, to preserve exact `Decimal` precision over the wire), `net_pay_clp` here is a plain JSON **number**, rounded to the nearest peso (no decimals) -- CLP has no subunit, and this field is a projection/approximation for `future` entries anyway, never a value persisted or reconciled against, so string-precision round-tripping does not apply the way it does for every other money field. The current period is the latest payroll with `declared_net_pay_clp` present and `payment_date <= today`. When none exists, the endpoint falls back to the current calendar month and infers missing periods from the configured employer payment rule or the default last Chilean business day of month. `net_pay_clp` for `future` entries is predicted, never declared: the first future month re-prices the current period's income/discounts to UF via `pf-rates` (30-day-prorated if the current period itself was partial); every subsequent future month replicates that same predicted amount unless it lands on an `increase: true` month (determined by the employer's `first_increase_period`/`increase_frequency` configuration), in which case it is stepped by the ratio between the latest published `IPC_CL` value and the `IPC_CL` value at the last real increase month before stepping, then replicated again until the next increase month -- except when that ratio would be a *decrease* (latest `IPC_CL` below the prior increase month's), in which case the previous amount is held flat instead, since salaries are never projected downward from deflation. If `pf-rates` is unreachable, or IPC data for the stepping calculation is missing/stale, the affected `net_pay_clp` values degrade to `null` (first-month prediction) or hold at their last known value without stepping (replication) rather than failing the whole request. |
| `GET` | `/payroll/summary` | Lists payroll period totals from `PAY_MV_SUMARY`. |
| `GET` | `/payroll/spreadsheet/template` | Downloads a blank CSV/XLSX spreadsheet shell (`format=csv` default, or `format=xlsx`) with the exact wide-format column headers `POST /payroll/import/spreadsheet` expects -- zero data rows, just the header row, so a human never has to guess column names from `docs/payroll-workflow.md` by hand. Derived from the same column-order helper the real export below uses, so it can never drift from that export's own header row. Never reads the database -- no `X-Api-Key`-scoped data leaves this endpoint, only a static shell. |
| `GET` | `/payroll/spreadsheet` | Bulk-exports every persisted payroll period matching the given filters (`employer`, `period_year`, `period_month`, all optional -- omitting all three exports every persisted period, same "no filter means everything" behavior as `GET /payroll/summary`) as a CSV/XLSX file (`format=csv` default, or `format=xlsx`), one row per period, in the same wide format `POST /payroll/import/spreadsheet` accepts. Columns are the blank template's columns (see above) plus two extra, append-only columns -- `income_tax` and `unemployment_insurance` -- for the two concepts that are computed by their own use case (`POST /payroll/{period_id}/compute-tax`, `POST /payroll/{period_id}/compute-contributions`) rather than declared via any import column; **`POST /payroll/import/spreadsheet` silently ignores those two extra columns on re-import** rather than rejecting or persisting them (it only ever reads columns it recognizes from the wide format), so exporting and re-importing the exact same file is safe and idempotent for every *other* column. A filter matching zero periods still returns a valid header-only file (HTTP 200), never an error. Response is a raw file download (`Content-Disposition: attachment`), not JSON. In the `format=xlsx` variant, every money column (all columns except `period_month`/`period_year`/`employer`/`payment_date`/`worked_days`/`employment_contract_kind`) is written as a real numeric cell with a `#,##0.00` number format -- not a text string -- so Excel renders the decimal separator per the *opening user's own locale* (e.g. `,` in `es-CL`, `.` in `en-US`) instead of showing a literal `.` regardless of locale. `format=csv` is unaffected by this (plain text, always `.` as the decimal point, matching what `POST /payroll/import/spreadsheet` expects on re-import). |
| `GET` | `/payroll/{period_id}` | Returns a payroll period with employer, items, selected plans, and summary. |
| `POST` | `/payroll/{period_id}/assign-plans` | Assigns pension and health plan snapshot ids to a payroll period. |
| `POST` | `/payroll/{period_id}/compute-contributions` | Computes pension, health, and unemployment insurance discounts. |
| `POST` | `/payroll/{period_id}/compute-tax` | Computes Chilean monthly income tax withholding. |
| `POST` | `/payroll/{period_id}/review` | Marks a payroll period as `reviewed` once required computed items exist. |
| `POST` | `/payroll/{period_id}/deflate` | Converts nominal payroll totals into real CLP using an economic index such as `IPC_CL`. |

### PDF templates

Manages the versioned employer-specific label-to-concept mapping templates `POST
/payroll/pdf-preview` matches PDFs against. Persisted in pf-db's `PAY_PDF_TEMPLATE` /
`PAY_PDF_TEMPLATE_FIELD` tables, not a git-tracked file -- see
[`docs/proposals/pdf-template-management-design-recommendation.md`](proposals/pdf-template-management-design-recommendation.md)
for why. Registered *before* the `/payroll/{period_id}` route in `interfaces/api/main.py`
(same reason as `/payroll/spreadsheet` above): a single-segment path param with no type
converter would otherwise swallow `GET /payroll/templates` as `period_id="templates"`.

| Method | Path | Description |
| --- | --- | --- |
| `POST` | `/payroll/templates` | Creates a new template. Body: `employer_id` (required -- the employer must already have a `PAY_EMPLOYER` row, i.e. its first payroll import has already run; there is no standalone endpoint to create one ahead of that), `employer_match_pattern`, `version` (defaults to `1`), and `fields` (at least one required -- a template with zero fields could never clear the 3-field `MIN_TEMPLATE_MATCH_SCORE` needed to even be selected; each field is `pdf_label_pattern`/`concept_code`/`confidence`, no `kind` -- the server always resolves a field's kind from `PAY_CONCEPT` via `concept_code`, never a client-sent value). `employer_id` is an admin-only FK into `PAY_EMPLOYER`, never read by the actual PDF-matching logic (which only ever uses `employer_match_pattern`); the response's `employer_name` is always resolved fresh from `PAY_EMPLOYER.name` at read time, never stored on this table. Every regex (`employer_match_pattern` and each field's `pdf_label_pattern`) is compile-checked by a Pydantic validator before ever reaching the database -- an invalid pattern is a `422`, not a crash the next time an unrelated PDF is previewed. Returns **201** with the created template (`is_active: true`). A duplicate `template_id`, a field whose `concept_code` does not exist in `PAY_CONCEPT`, or an `employer_id` that does not exist in `PAY_EMPLOYER`, is a **400**. |
| `GET` | `/payroll/templates` | Lists templates, active-only by default. `?include_inactive=true` also returns logically-deleted ones. |
| `GET` | `/payroll/templates/{template_id}` | Returns one template by its external `template_id`, active or not (a direct lookup by id always finds it regardless of status). **404** if no template has ever existed with that id. |
| `PUT` | `/payroll/templates/{template_id}` | Replaces an existing template's employer metadata and fields **in place** -- mutates the row, does not create a new `template_id`/version (bumping `version` is a plain field edit in the request body, not automatic). Same body shape and validation as `POST`, minus `template_id` (taken from the path). **404** if the template doesn't exist (never a silent create); **400** on the same constraint violations as `POST`. |
| `DELETE` | `/payroll/templates/{template_id}` | Logical delete only -- sets `is_active: false`; never a row `DELETE`. Returns the now-inactive template. **404** if the template doesn't exist. A subsequent `POST /payroll/pdf-preview` will no longer match against it, but `GET /payroll/templates/{template_id}` (and `?include_inactive=true` on the list) still finds it. |

## CLI

Run the CLI with:

```bash
python -m payroll.interfaces.cli.main <command>
```

Or use the Makefile shortcut for payroll import:

```bash
make import-payroll CSV_FILE=docs/payroll-input.csv
```

Available commands:

| Command | Purpose |
| --- | --- |
| `health` | Basic healthcheck. |
| `import-payroll <file>` | Imports a CSV/XLSX payroll file. Runs on the same transactional-scope machinery as `POST /payroll/import/spreadsheet`: the whole import + reconciliation pipeline runs inside one SAVEPOINT, and only actually commits once every period reconciles cleanly -- a genuine declared-vs-computed conflict rolls everything back and fails the command with a non-zero exit code instead of persisting partially-reconciled data. On that failure, stderr prints the plain message first, then (on its own line) the same structured `{"message": str, "conflicting_periods": [...]}` detail as the HTTP endpoint's 400 `detail` -- listing only the period(s) that actually conflicted, so a multi-period file does not require scanning every clean one by hand. |
| `template-test <pdf>` | Previews a payroll PDF against the current **active** templates (read from pf-db, via the same `TemplateReader` the HTTP endpoint uses) without persisting anything -- prints which template matched (if any) and which rows are still unresolved. `payment_date` is always the generic "last business day of the month" guess here, never the employer's real configured rule (unlike `POST /payroll/pdf-preview`, which does resolve it when the employer is registered). This command used to need **no database access at all** when templates lived in a git-tracked JSON file; moving templates into pf-db means it now opens a read-only DB session like every other CLI command does, purely to fetch the current templates. Helper for sanity-checking a template managed via `POST`/`PUT /payroll/templates*` against a real PDF before trusting it in production. |
| `summary` | Lists payroll period summaries. |
| `period-detail <period_id>` | Returns one payroll period with detail. |
| `plan-snapshots` | Lists available pension and health plans. |
| `assign-plans <period_id> <pension_plan_id> <health_plan_id>` | Assigns period plan snapshots. |
| `compute-contributions <period_id> <pension_plan_id> <health_plan_id> [--uf-value-clp]` | Computes social-security discounts. |
| `compute-tax <period_id> [--utm-value-clp]` | Computes income tax withholding. |
| `review <period_id>` | Marks a period as reviewed. |

All CLI commands emit JSON except `health`.
